### Summary

Day one. I set up the project end to end, from an empty folder to a deployed (blank) app at its real address, and planned everything after it. I created the roadmap and file architecture, chose the tech stack, and decided to build with an agile process, starting with a preliminary backlog.

### Why agile

I'm building this alone around classes, so instead of designing the whole app up front, I'm working in short sprints. Each sprint picks a few items from the top of the backlog and ends with something working and deployed, even if it's rough. After each one I review what I shipped, note what went well and what didn't, and adjust the next sprint.

This fits the project because the parts I care most about, the reading analytics and the profile bookshelf, are easier to get right once I'm using early versions with my own data.

- Features are written as **user stories** ("As a reader, I want…") with acceptance criteria that define done
- Big features are **epics**, split into smaller stories when they get close to the top
- **Done** means deployed and working, not just working locally
- New ideas go into the backlog instead of the current sprint

### Tech stack

| Layer | Choice | Why |
| --- | --- | --- |
| Frontend + API | Next.js (React) | Server-side API routes keep the database credentials and API keys out of the browser, and my portfolio already runs on it |
| Hosting | Vercel | My portfolio is already there |
| Database | Neon Postgres | Least setup: it plugs straight into Vercel, with a free tier |
| Book data | Open Library, with Google Books as a fallback | Open Library is free with no key; each book gets saved to my database the first time it's looked up, so later searches are local |
| Address | victoriasun.xyz/projects/book-tracker | No new domain; the portfolio forwards this path to the app |

Other decisions:

- **Books are keyed by ISBN-13.** ISBN-10s get converted on input, and I also store the Open Library work ID, since every edition has its own ISBN.
- **Every read is its own row,** so rereads, per-read dates, and per-read ratings work without special cases.
- **The API is versioned under `/api/v1`** so a Swift iOS app can share the same backend later.

<summary>Epic 2 · Accounts</summary>

**Story 1: Sign up**
*As a new user, I can create an account with a unique username and a password.*

- A taken username shows an error and doesn't create an account
- The password is hashed with bcrypt or argon2, never stored as plain text
- After signing up, I'm logged in

**Story 2: Log in and out**
*As a user, I can log in, stay logged in between visits, and log out.*

- A wrong username or password shows one general error, without saying which part was wrong
- The session lasts across visits until it expires or I log out
- On the web the session is a cookie scoped to `/projects/book-tracker`; the future iOS app will use a token instead
- Logging out ends the session on the server, not just in the browser

**Story 3: My data stays mine**
*As a user, only I can change my shelves.*

- Every route that edits shelves checks who's logged in
- Trying to edit another user's data is rejected

**Done when** two test accounts can log in and each sees only their own shelves.

**Tasks**
- [ ] `users` and `sessions` tables
- [ ] Password hashing helpers
- [ ] Sign-up, login, and logout API routes
- [ ] Session check shared by every protected route
- [ ] Sign-up and login pages

CAPTCHA and login rate limiting come later, once there's a baseline product.
